# 데이터 수집 전략

## 결론: 자동 다운로드 + 사람이 눈으로 검수하는 하이브리드

순수 자동 크롤링(다운로드+라벨 전부 자동)도, 순수 수동(구글에서 한 장씩 찾아 저장)도 둘 다 비효율적이다.

- **순수 자동 크롤링만 쓰면**: 검색어나 쇼핑몰 카테고리("손잡이 머그컵" 등)가 우리 분류 규칙(높이/지름 비율, 꺾임 유무 같은 실루엣 기준)과 정확히 안 맞는다. 카테고리만 믿고 라벨을 확정하면 오염된 데이터가 섞인다.
- **순수 수동으로 구글에서 하나하나 찾아 저장하면**: 라벨은 정확하지만 320~400장을 모으는 데 시간이 너무 오래 걸린다.
- **그래서**: 다운로드는 자동으로 빠르게 받고, **라벨 확정은 사람이 4종 규칙으로 한 장씩 눈으로 확인**해서 `train/{class}` 또는 `data/_hold`로 분류한다. 이게 README의 "애매하면 `_hold`로 분류 — 주 1회 팀원 전원이 함께 판정" 규칙과도 맞는다.

## 소스별 방법과 우선순위

1. **네이버 쇼핑 API (1순위, 공식)**
   - 공식 API라 이용약관 문제 없음. 상품 카테고리는 참고만 하고, 최종 라벨은 사람이 확인.
   - API 키(클라이언트 ID/시크릿) 발급 필요 — 네이버 개발자센터에서 무료 발급.

2. **검색 엔진 이미지 크롤링 (2순위, 부족분만)**
   - `icrawler` 파이썬 라이브러리 사용 — `GoogleImageCrawler`, `BingImageCrawler` 둘 다 제공.
   - **구글은 공식 API가 아니라 검색 페이지를 직접 파싱하는 방식**이라 참고할 점이 있다:
     - 구글 이용약관상 자동 스크래핑은 엄밀히는 위반
     - 구글이 페이지 구조를 바꾸면 가끔 깨짐
     - 너무 빨리 많이 요청하면 일시적으로 막힐 수 있음
     - 소규모 비상업 학습 프로젝트에서는 실무적으로 널리 쓰이지만, 완전 공식은 아니라는 점은 인지하고 사용
   - **빙(Bing)이 상대적으로 더 안정적**이라 구글과 같이 돌려서 서로 보충하는 걸 추천.
   - (참고) 완전히 공식 경로를 원하면 Google Custom Search JSON API도 있으나, 무료 쿼리가 하루 100회로 제한적.

3. **직접 촬영 (Test 전량)**
   - 자동화 대상 아님. README 촬영 프로토콜(각도/배경 3종 이상/조명/뚜껑 열림·닫힘) 그대로 따름.
   - 개인거래 플랫폼(당근 등)은 약관·사생활 문제로 수집 대상에서 제외.

## 클래스별 검색어 제안 (초안)

| 클래스 | 검색어 예시 |
|---|---|
| `straight` (직선 원통형) | 일자 텀블러, 스트레이트 텀블러 |
| `taper_smooth` (연속 테이퍼형) | 테이퍼 텀블러, 커피 텀블러 |
| `taper_step` (단차 테이퍼형) | 스탠리 텀블러, 퀜처 텀블러 |
| `mug` (머그형) | 손잡이 머그컵, 스텐 머그컵 |

검색어는 후보를 넓게 모으기 위한 것일 뿐, 최종 라벨은 반드시 4종 판정 규칙(CLAUDE.md 참고)으로 사람이 확인한다.
